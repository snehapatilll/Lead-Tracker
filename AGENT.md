Documentation of AI tool usage in building this project, as required by the
assignment brief.

| --- | --- | --- |

No other AI tools were used. No code was copied from Stack Overflow, tutorials,

## Context

The project was built in a **single working session** after an earlier attempt
was lost: the original laptop failed and Claude Code stores session transcripts
locally rather than in the account, so moving to a second machine meant no
history and no code carried over. The rebuild started from the assignment brief
alone, against a next-day deadline.

That constraint shaped several decisions below — most visibly the choice to
keep the whole thing in one language and one deployable unit.

---

## How the work was split

### Directed by me (human)

These were decisions, not generated output. The AI presented options and
trade-offs; the choices were mine.

- **Backend stack.** Offered Node/Express/TS, FastAPI, and NestJS. Chose
  Express + TypeScript: one language across the repo, and NestJS's structure
  was not worth the boilerplate at this size and deadline.
- **Database and hosting.** Offered Neon+Render, Atlas+Render, and a
  three-service split. Chose Neon + a single Render service — one URL, no CORS
  surface, fewest moving parts to break the night before a deadline.
- **Scope.** Held the feature set to the brief. Rejected the temptation to add
  auth, CSV import, or a dashboard.
- **Priorities.** Required that the test suite run without a database, and that
  the README document real trade-offs rather than list technologies.

### Generated by AI

Effectively all source code, written from my prompts and then reviewed:

- `server/src/**` — domain types, zod schemas, repositories, routes, Express
  app, bootstrap
- `client/src/**` — API client, `useLeads` hook, all components, CSS
- `server/tests/leads.test.ts` — the 25-test suite
- `README.md`, `AGENT.md`, `render.yaml`
- Environment setup (installing Node, resolving a failed installer)

### Reviewed and corrected

The output was not accepted blindly. Specific interventions:

- **A stray token in `LeadForm.tsx`.** The word `challenge` was emitted into
  the middle of a JSX attribute list — invalid syntax that would have failed
  the build. Caught and removed before committing.
- **An aborted-request bug.** The first version of `lib/api.ts` caught every
  `fetch` rejection and rewrote it as "Could not reach the server." That
  included `AbortError`, which is thrown deliberately whenever a superseded
  search is cancelled — so typing quickly would have flashed a spurious network
  error. Fixed by re-throwing `AbortError` untouched.
- **A production-safety gap.** The no-database mode was initially just a
  convenience flag. It was changed to hard-refuse `NODE_ENV=production`, so a
  misconfigured deploy fails loudly at boot instead of silently losing every
  lead on each restart.
- **Verification, not assumption.** The full stack was run locally and
  exercised end to end — every endpoint via HTTP, plus the real UI in a browser
  — before anything was called done.

## Prompts used

Paraphrased to the substance; the session was conversational rather than a
list of one-shot prompts.

**1 — Environment**
> "This system may not have Node.js. Install the necessary dependencies."

Led to discovering Node was missing and the winget installer's admin prompt
being cancelled (exit 1602). The AI fell back to a portable Node zip extracted
into the user profile, which needs no elevation. Worth noting as a genuinely
useful recovery rather than a retry loop.

**2 — Scaffolding**
> Build a Lead Tracker per the brief: React + TypeScript frontend, backend of
> my choice, Postgres or Mongo, with create / list / search / update-status
> over name, email, phone, status, created_at.

**3 — Testability constraint**
> The test suite must run with no database. A grader who clones this and runs
> `npm test` should see it pass.

This is the prompt that produced the repository-interface design. Without it
the AI's default would have been to call `pg` directly from the route handlers
and write tests requiring a live database.

**4 — Deployment shape**
> One service, one URL. Express should serve the built React app in production.

**5 — Documentation**
> The README's trade-offs section must state what each decision actually costs,
> not just what was chosen. The same for the known gaps in test coverage.

Produced the honest notes about `ILIKE` not using an index, the untested
Postgres repository, and `rejectUnauthorized: false`.

## Key engineering decisions

**Repository interface between routes and Postgres.**
`routes/leads.ts` depends on a `LeadRepository` interface with two
implementations — Postgres and in-memory. The HTTP layer contains no SQL, and
the test suite exercises the real Express stack against the in-memory double.
Cost: one extra indirection, and the Postgres implementation has no automated
test of its own. Documented as the top gap in the README.

**Single deployable unit.**
Express serves `client/dist` in production. One build, one URL, no CORS, no
environment-specific API base URL to get wrong. Vite's dev proxy preserves hot
reload locally. Cost: frontend and backend cannot scale independently — which
is irrelevant at this size.

**zod as the single source of input truth.**
Every request body and query string is parsed by a schema that also supplies
defaults and coercion. `LEAD_STATUSES` is declared once in `domain.ts` and
drives the zod enum, the Postgres `CHECK` constraint, and the client dropdown,
so adding a status is a one-line change plus a migration.

**Errors that do not leak.**
Only `ApiError` instances are rendered to the client. Anything else is logged
server-side and returned as a generic 500, so driver messages and connection
strings never reach a response body. Validation failures return field-keyed
details, which the form maps back onto individual inputs.

**Sort columns are whitelisted, not interpolated.**
Column names cannot be parameterised in SQL, so `sort` is mapped through a
`Record` rather than concatenated into the query. Everything else uses bound
parameters.

**Pagination total in the same round trip.**
`COUNT(*) OVER()` returns the pre-pagination total alongside the page, avoiding
a second query.

**Debounced search with cancellation.**
300ms debounce plus an `AbortController` per request, so a fast typist issues
one request rather than one per keystroke, and a slow earlier response cannot
overwrite a newer one.

## Honest assessment

AI wrote the overwhelming majority of the characters in this repository. What
it did not do was decide what to build, choose the stack, impose the
no-database testing constraint that drove the architecture, catch the invalid
JSX before it was committed, or notice that swallowing `AbortError` would
produce phantom network errors under fast typing.

The review step was not a formality. Two of the three defects above would have
shipped — one breaking the build outright, the other producing an
intermittent bug that is unpleasant to diagnose after the fact.
